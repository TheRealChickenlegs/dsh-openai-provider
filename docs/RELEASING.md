# Release Process (automatic GitHub Release + npm publish)

This repository has two release pipelines, **both driven by tags**; no local publish command is needed:

| Workflow | Trigger | What it does |
|---|---|---|
| [release.yml](../.github/workflows/release.yml) | pushing a `v*.*.*` tag | creates the GitHub Release, with notes generated by GitHub from the commits |
| [publish.yml](../.github/workflows/publish.yml) | pushing a `v*.*.*` tag / a Release being published / manual dispatch | `npm test` → `npm publish --provenance --access public` |

Push one tag and both pipelines run **independently**: the Release is created and npm is published.

> ⚠️ **publish.yml must listen for tag pushes itself; it cannot rely on the release event alone**: release.yml uses
> the repository's built-in `GITHUB_TOKEN`, and GitHub specifies that **events produced by `GITHUB_TOKEN` do not trigger
> other workflows** (to prevent recursion), so the "Release just created" event never reaches publish.yml. The
> release-event trigger is kept to cover "a human manually publishes a Release in the GitHub UI".

---

## One-Time Setup: Add NPM_TOKEN

Publishing to npm needs credentials, and credentials are **not stored in code** — only in a GitHub repository secret,
which is never written to logs or exposed in PRs.

1. Open <https://www.npmjs.com/settings/~/tokens> and click **Generate New Token**. The current UI goes straight to the
   **New Granular Access Token** form.
2. Fill it in like this:

   | Field | Value | Why |
   |---|---|---|
   | Token name | anything, e.g. `dsh-openai-provider-ci` | Easier to recognise when rotating |
   | Expiration | **90 days** (the longest the UI offers) | After expiry CI publishing fails; see "Rotation" below |
   | **Bypass two-factor authentication (2FA)** | **check it** | Otherwise publishing asks for a phone code and the unattended pipeline hangs |
   | Packages and scopes → Permissions | **Read and write (publish and stage)** | `stage only` **cannot publish** |
   | Organizations | **No access** | A personal package does not need org permissions |
   | Allowed IP ranges | **leave empty** | GitHub Actions egress IPs change every time |

3. **Copy the token immediately** after saving (it starts with `npm_` and is shown only once).
4. Open <https://github.com/TheRealChickenlegs/dsh-openai-provider/settings/secrets/actions> and click
   **New repository secret**:
   - Name: `NPM_TOKEN` (exactly — that is the name the workflow reads);
   - Secret: paste the token, then save.

No code changes are needed after this setup.

> **What if it is not configured?** The guard in `publish.yml` detects the empty `NPM_TOKEN`, **skips** the npm publish
> and leaves a notice in the run summary — the workflow stays green. Forks that push tags therefore do not turn red.

> **Rotation**: a Granular token lasts at most 90 days. After expiry `publish.yml` fails at the publish step (401 /
> permission error). Delete the old token, generate a new one, and update `NPM_TOKEN` — no code or version change.
> Never paste the token into chat, an issue, or a commit; if you suspect a leak, revoke it and regenerate immediately.

## Publishing a New Version

Keep these places consistent:

| Place | What to change |
|---|---|
| `package.json` | `"version": "x.y.z"` |
| `src/identity.ts` | `PLUGIN_VERSION = 'x.y.z'` (a test fails if it differs from package.json) |
| `CHANGELOG.md` | add a dated section for the release |
| Git tag | `vx.y.z` — must match `package.json` exactly |

```bash
# 1. Bump the version and the changelog, then build the committed lib/
npm version x.y.z --no-git-tag-version
npm run build

# 2. Commit everything (including regenerated lib/ and the client bundle)
git add -A
git commit -m "chore: release vx.y.z"

# 3. Tag and push. The tag must start with v and match package.json.
git tag -a vx.y.z -m "vx.y.z"
git push origin main
git push origin vx.y.z
```

After pushing the tag:

- the **Release** workflow creates <https://github.com/TheRealChickenlegs/dsh-openai-provider/releases>;
- the **Publish to npm** workflow publishes the package.

`publish.yml` reads the package name from `package.json`, so renaming the package does not require workflow changes.

**Guard one — version/tag match.** If the tag is `v0.2.0` while `package.json` says `0.1.0`, the workflow fails
immediately with an explanation. npm cannot republish a version, so this guard prevents publishing the wrong code.

**Guard two — idempotency.** If the version already exists on npm, the workflow prints a notice and skips publishing
instead of hitting npm's 403. Repeat triggers (for example publishing the Release again in the UI) stay green.

**Guard three — committed `lib/`.** `publish.yml` rebuilds and runs `git diff --exit-code -- lib` before testing, so a
tag whose committed build is stale fails instead of shipping different code from the source.

## Manual Re-Release / Backfill

- **Backfill the Release for an old tag**: Actions → Release → Run workflow, enter the tag (e.g. `v0.1.0`). An existing
  Release is skipped rather than erroring.
- **Manually publish to npm**: Actions → Publish to npm → Run workflow; enter a tag (e.g. `v0.1.0`) — it checks out
  **the code that tag points at** and publishes it. Leaving it empty uses the default branch's `package.json` version.
  Versions already published are skipped.
- **Publish locally by hand** (fallback):

  ```bash
  npm login --registry=https://registry.npmjs.org
  npm run build
  npm test
  npm publish --provenance --access public
  ```

  If the machine is configured with a mirror registry, specify the official registry explicitly before publishing.

## Provenance (verifiable origin signature)

`npm publish --provenance` signs the package with the GitHub Actions OIDC identity: npm shows a **Built and signed on
GitHub Actions** badge, and anyone can verify the package came from this repository. That is why `publish.yml` requests
`id-token: write`.

Prerequisites: the repository is **public** and `package.json` has a `repository` field — this repository satisfies both.

## What the Published Package Contains

Decided by `package.json`'s `files` field (not `.npmignore`): `lib/` (build output, **committed on purpose**, so users
need no TypeScript), `src/`, `scripts/`, `docs/`, `tsconfig.json`, `cordis.patch.yml`, `icon.svg`, the README,
`CHANGELOG.md`, and `LICENSE`.

To preview the list before publishing:

```bash
npm pack --dry-run
```
